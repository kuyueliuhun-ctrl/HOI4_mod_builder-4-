## 1. 大洲划分（大陆归属）

### 1.1 是否有现成洲别字段：有（definition.csv 第 8 列，原生、省级）

逐项核查：

| 文件 | 是否有洲别 | 说明 |
|---|---|---|
| `map/continent.txt` | 只有**洲名列表** | 声明 7 个洲：`europe / north_america / south_america / australia / africa / asia / middle_east`（mod 与游戏完全一致）。**不含州→洲映射**。 |
| `map/strategicregions/*.txt` | ❌ | 只有 `id / name / provinces / weather`，无洲字段。 |
| `map/supplyareas/*.txt` | ❌ | 只有 `id / name / value / states`，无洲字段。 |
| `history/states/*.txt` | ❌ | state 块内无 `continent` 键（全库 grep 0 命中）。 |
| `common/state_category/*.txt` | ❌ | 只有 `local_building_slots / color / 生产修正`。 |
| `map/definition.csv` | ✅ **有（第 8 列）** | 每省一行的第 8 列取值 **0–7**：`0`=水域（ocean/lake，无洲），`1–7` 恰好对应 `continent.txt` 的 7 个洲（序号 +1 偏移）。 |
| `map/positions.txt` | ❌ | **0 字节**（mod 与游戏都是空文件），无坐标可用。 |

**第 8 列 ↔ 洲 的映射（经 967 个游戏州 / 1485 个 mod 州全量交叉验证）：**

```
0  = 水域（无洲）      （ocean/lake 省全为 0；全游戏仅省 0 一个 land 例外）
1  = europe           （法国、意大利、冰岛、波兰…）
2  = north_america    （USA、加拿大、墨西哥、格陵兰、中美洲…）
3  = south_america    （巴西、阿根廷、乌拉圭、加勒比、中美洲在引擎内归此…）
4  = australia        （澳、新、新几内亚、太平洋岛链…）
5  = africa           （北非埃及/利比亚/摩洛哥、撒哈拉以南…）
6  = asia             （USSR/俄罗斯亚洲部分、印、中、日、东南亚…）
7  = middle_east      （土耳其、高加索、伊朗、伊拉克、沙特、也门…）
```

即：**`definition.csv 第 8 列 = continent.txt 中的序号 + 1`**，`0` 保留给水域。这是游戏原生、每省一条、精确到大洲边界（俄乌界州、伊斯坦布尔州都是按省精确拆分）的数据源。

### 1.2 州→大洲 聚合（与引擎一致的多数表决）

- 每个州取它所有省的第 8 列做多数表决（仅统计非 0 列）。实测：
  - mod 1485 州中 **1468 个州 ≥80% 的省同洲**；仅 11 个州跨洲，且全部是合理边界州（俄欧/亚界：Arkhangelsk、Volgograd、Saratov 等；伊斯坦布尔/爱琴海诸岛 1↔7）。对这些州多数表决与引擎判定一致。
  - 游戏侧同理（如 state 1 France→1、state 300 Uruguay→3、state 683 NE Canada 的湖省为 0 但陆省为 2）。
- 可选兜底：「国家→大洲」= 该国**首都州**的大洲（`history/countries/*.txt` 顶部有 `capital = <state_id>`，已确认格式），用于无州/无核心的边缘情况或 UI 校验。

### 1.3 推荐方案 A：definition.csv 原生洲列 → 州聚合（不推荐 GeoJSON / 外部表）

- **数据源**：`map/definition.csv` 第 8 列（mod 优先、游戏兜底）。**现有代码已经读了这个列**：`src/map_loader.py:84` 把 `parts[7]` 存为 `province_table[pid]["region"]`——只是命名误导（叫 region），且全库目前没有任何地方消费它，正好留给本项目复用。
- **洲名序**：`map/continent.txt` 列表（两份一致）即显示用枚举。
- **为何不做 GeoJSON 投影 / 外部国家→大洲表**：
  1. 引擎原生数据已存在且零误差，外推/投影只会引入误差（尤其 mod 自定义地图 `provinces.bmp` 5632×2048，坐标系与真实经纬度无保证对应）；
  2. `positions.txt` 为 0 字节，无原生经纬度可投影；
  3. 国家→大洲表按 tag 归属会丢失「州粒度」且 TFR 是总转换 mod，自定义 tag（A24、74th Group Army 等）外部表不可用。

## 2. 核心圈层（国家核心 + 邻接分层）

### 2.1 `add_core_of` 字段格式（已确认）

格式：`state.history` 块内的**重复标量键** `add_core_of = TAG`（每行一个，TAG 为裸标识符大写，不带引号）。已抽查：

- 游戏 `history/states/1-France.txt`：`add_core_of = COR` / `add_core_of = FRA`
- mod  `history/states/1-France.txt`：`add_core_of = FRA` / `add_core_of = COR`
- mod  `history/states/1027-Idlib.txt`：`add_core_of = SYR` / `add_core_of = HTS`
- mod  `history/states/1000-Louisville.txt`：`add_core_of = USA`

**全库扫描**（统计截至 2026-08-26 05:35 UTC）：

| 数据源 | state 文件/块数 | 含 core 的州 | core 条目总数 | 不同 tag 数 |
|---|---|---|---|---|
| 游戏本体 | 1081 | 1057 | 1590 | 314 |
| mod（TFR） | 1493 | 1436 | 1733 | 218 |

扫描中**未发现**块形式（如 `add_core_of = { TAG1 TAG2 }`）；解析时按行形式（每行一个 value 键）即可，但建议用 `parse_pdx_text_to_nodes` 通用解析以免漏掉其它 mod 写法。一个州可有多个 core（如法国科西嘉 `FRA`+`COR`），即 `tag→州集合` 是多对多。

> 注意：mod 的州文件数 = 1493（1485 个 `N-名.txt` + 8 个 `N - 名.txt` 带空格前缀），游戏 = 1081。文件名前缀不一定全匹配 `^\d+-`，解析应**按块**（`state = {`…`}` + `id` 键）而不是按文件名正则。

### 2.2 现有数据层缺口

`src/state_loader.py` 的 `StateData._parse_history()` **目前不解析 `add_core_of`**（只处理 `owner / name / resources / buildings / victory_points`）。这是方案 B 唯一的解析改动点。`StateData` 已有：
- `states: dict[state_id, info]`（info 含 `provinces`、`owner`、`src`…）
- `province_to_state: dict[pid, state_id]` 反查索引 —— 邻接聚合直接可用。

渲染层已有现成原语：
- `map_data_layers.build_categorical_overlay(idm, pid_cat, alpha)` —— 按省分类着色，**大洲（8 色）和圈层（k 色）都直接复用**。
- `map_data_layers.load_supply_areas` / `map_editor_dialog._apply_data_layer` 里的「补给区」分支演示了正确的 **state→省展开** 写法。

> ⚠️ 顺带发现的现有 bug（与本任务相关，写新层时注意）：`_apply_data_layer` 的「胜利点/资源」分支直接把 `{state_id: 值}` 当 `{pid: 值}` 传给 `build_value_overlay`，着色是按「省 id == 州 id」的巧合，基本是错的。新的大洲/圈层层**必须**按「补给区」分支模式做 state→省展开。

### 2.3 州邻接的构建（核心圈层 BFS 的地基）

现无现成州邻接实现。推荐从**已加载的 `MapData.id_map`（provinces.bmp 像素矩阵）**派生：

1. 向量化邻域扫描：`id_map` 与其右邻/下邻逐像素不等 → 省邻接对（去重、去 0）。
2. 过滤 `land-land`（用 definition.csv 的 type）。
3. 经 `province_to_state` 聚合成 `state 邻接对`。

**实测（mod 地图，TFR 自定义，5632×2048）：**

| 步骤 | 耗时 |
|---|---|
| id_map 构建（RGB→id LUT） | 0.56s |
| 省邻接对扫描（全部类型） | 0.22s |
| land-land 州邻接对 | 0.07s（3361 对） |

- 陆省 11724 个，其中 **49 个不属于任何州**（边缘小岛/废省，聚合时跳过即可）。
- **114 个州无陆上邻接**（纯岛州，如英国、冰岛、印尼、太平洋岛链）。这直接影响圈层语义：默认「仅陆邻」时岛州 ring≥1 为空；如希望海峡可达（英国↔欧洲、日本↔朝鲜），可选并入 `map/adjacencies.csv` 的海峡/海上通道（mod 213 行、游戏 256 行，格式 `From;To;sea;Through;…`）。
- 缓存建议：州邻接图可按 `(mod_path, mtime 摘要)` 落盘 pickle/缓存（`map/definition.csv + provinces.bmp + states 目录` 任一变化即失效），避免每次启动重扫。

### 2.4 核心圈层计算（BFS 分层）

语义：
- **ring 0** = 该国核心州（`add_core_of` 集合）。
- **ring k (k≥1)** = 到最近核心州的最短「州邻接路径」恰为 k 的州（BFS，按层展开）。
- **不可达** = INF（无边可通的州），默认不染色或置灰。
- 可设 `max_ring`（如 6），`ring ≥ max` 统一归入「更远」桶，避免过宽色带。

数据源：`history/states/*.txt`（mod 优先 + 游戏兜底，复用 StateData 目录优先级）+ 上节邻接图。

- **工作量**：**M**（StateData 解析改动 + 邻接构建 + BFS + UI 图层/国家选择 + 缓存）。
- **主要风险**：
  1. 孤立岛州默认无邻接 → 圈层中断（需产品决策：仅陆邻 vs 含海峡；TFR 是现世界场景，含海峡更合理）。

## 3. 通用落地建议（两方案共用）

1. **渲染统一走 `build_categorical_overlay`**：大洲（8 类：7 洲 + 无洲/水域）、圈层（k 类 + 不可达）。两层的 state→省展开都照「补给区」分支写，**不要**照「胜利点/资源」分支写。
2. **缓存**：新派生数据（州→洲、州邻接、tag→核心州）建议一次性构建并缓存（进程内 LRU + 可选 pickle），失效键 = `(mod map/definition.csv、provinces.bmp、continent.txt、history/states 目录的 mtime/大小摘要)`。写回 state 后触发失效（`StateData.reload()` 已有，可挂钩）。
3. **命名修正**：`map_loader.py` 的 `"region"` 字段（实为大洲）建议改名 `"continent"` 或加 `continent` 别名；`api_core_ext/states.py::_province_meta` 的列错位 bug 应顺手修（与新功能相关，避免未来误用）。
4. **中文显示**：洲名中文需自带表（游戏 localisation 无 `CONTINENT_<name>` 独立键，只有 `COLLECTION_STATES_IN_EUROPE` 这类组合键，不可直接复用）。
5. **取数快照**：本报告所有统计/抽查基于 2026-08-26 05:35 UTC；游戏为现行版本（`clausewitz_rev.txt` 等存在），mod 为 TFR 当前文件。实现前如 mod 更新，需重跑 §1.2 / §2.1 的统计脚本校验。
